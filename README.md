Этот код демонстрирует низкоуровневое ручное управление асинхронным рантаймом Tokio в языке Rust .
Вместо использования стандартного макроса #[tokio::main], который скрывает процесс инициализации, здесь разработчик самостоятельно настраивает конфигурацию операционной системы для планировщика задач с помощью структуры Builder .

------------------------------
## 🏃 Пошаговый разбор работы кода## Шаг 1: Конфигурация и сборка рантайма
```rust
let runtime = Builder::new_multi_thread()
    .worker_threads(4)
    .thread_name("thread-one")
    .thread_stack_size(3 * 1024 * 1024)
    .build()?;
```
С помощью строителя (Builder) создается многопоточный движок асинхронности со следующими жесткими параметрами :

* new_multi_thread() — включает архитектуру распределения задач Work-Stealing (многопоточный режим работы рантайма).
* worker_threads(4) — принудительно выделяет ровно 4 системных потока ОС под управление Tokio, независимо от того, сколько ядер у процессора на самом деле.
* thread_name("thread-one") — задает префикс имени для создаваемых потоков (удобно при анализе логов или отладке через утилиты вроде htop).
* thread_stack_size(3 * 1024 * 1024) — выделяет по 3 Мегабайта памяти под стек каждого рабочего потока (по умолчанию ОС выделяет меньше, это полезно для предотвращения падения от переполнения стека при глубокой рекурсии).
* .build()? — инициализирует рантайм. Знак вопроса ? означает, что если операционная система не сможет выделить потоки или память, функция main мгновенно завершится, вернув ошибку io::Result.

## Шаг 2: Фоновый запуск асинхронной задачи

runtime.spawn(async {
    println!("{}", fetch_network_request().await);
});


* Метод runtime.spawn берет асинхронный блок async { ... } и забрасывает его на выполнение в созданный пул из 4-х потоков .
* Этот метод работает как «выстрелил и забыл» (fire-and-forget): он не блокирует выполнение текущего кода и возвращает JoinHandle, который в данном случае игнорируется .

------------------------------
## 💥 Критическая логическая ошибка: Почему этот код ничего не напечатает?

Если вы скомпилируете и запустите этот код в текущем виде, на экране консоли ничего не появится, и программа завершится за доли миллисекунды.
Причина:
Метод runtime.spawn запускает задачу асинхронно в фоне . Сразу после вызова spawn главный поток функции main идет дальше и видит строку Ok(()). Программа успешно завершается.
Поскольку главный поток main координирует жизнь всего процесса, операционная система мгновенно уничтожает объект runtime и закрывает приложение, не дав фоновым потокам успеть сделать даже первый .poll() для функции fetch_network_request() .

------------------------------
## 🛠️ Как исправить код (2 правильных пути)
Чтобы программа дождалась выполнения фоновой задачи, главный поток должен заблокироваться до момента её завершения.
## Вариант А: Использование метода block_on (Рекомендуется для ручных рантаймов)
Метод block_on замораживает текущий поток main и заставляет его держать рантайм активным до тех пор, пока переданная асинхронная задача не вернет Poll::Ready .

fn main() -> io::Result<()> {
    let runtime = Builder::new_multi_thread()
        .worker_threads(4)
        .build()?;

    // block_on заставит программу дождаться завершения вычислений
    runtime.block_on(async {
        println!("{}", fetch_network_request().await);
    });

    Ok(())
}

## Вариант Б: Ожидание через JoinHandle
Если вам нужно запустить задачу именно через .spawn, сохраните её рукоятку управления и передайте её в block_on :

fn main() -> io::Result<()> {
    let runtime = Builder::new_multi_thread().build()?;

    // Сохраняем JoinHandle задачи
    let handle = runtime.spawn(async {
        fetch_network_request().await
    });

    // Блокируем main, пока handle не завершится
    let result = runtime.block_on(handle).unwrap();
    println!("Out: {}", result);

    Ok(())
}

## 💡 Когда оправдан ручной сборщик Builder?
В реальном продакшене макрос #[tokio::main] заменяют на структуру Builder в двух случаях :

   1. Вы пишете плагин или библиотеку (FFI), которая будет вызываться из кода на другом языке (например, C++ или Go) и вам нужно изолировать асинхронные потоки Rust от вызывающей программы.
   2. Вы пишете сложную архитектуру (например, ноду блокчейна Solana), где под разные задачи (сетевой IO, дисковые логи os.O_APPEND, валидация транзакций) выделяются изолированные пулы потоков с разными приоритетами и размерами стека, чтобы они не мешали друг другу.
